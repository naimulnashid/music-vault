# Landing Page Setup (apps/site)

The landing page, live at <https://music-vault-site.vercel.app/>, is a single static page built
with [Astro](https://astro.build). It explains what Music Vault is and sends visitors to the setup
guides and the repository. It is separate from the web app: every web app deployment is someone's
private player, so its home page cannot be a public page.

It ships no client framework and makes no third-party requests: the font is self-hosted, the
screenshots are the README's own (`docs/screenshots/`, imported at build time), and there is no
analytics. The only JavaScript is the screenshot tabs, closing the phone menu after a link is
chosen, and the light/dark toggle in the header; without it, both screenshot sets show one after
the other, the menu still works, and the page follows the system theme with the toggle hidden.

The theme follows the visitor's system setting until they pick one with the toggle. The choice
is saved in the browser (`localStorage`) and applied by a small inline script in `<head>` before
first paint, so a returning visitor never sees the other theme flash. Choosing the theme the
system is already on clears the saved choice.

## 1. Run locally

Astro needs Node 22.12 or later.

```sh
npm install
npm run site:dev      # http://localhost:4321, with hot reload
npm run site:build    # static output in apps/site/dist
npm run site:check    # type-check the .astro files
npx astro preview --root apps/site   # serve the built site on http://localhost:4321
```

No environment variables are needed.

## 2. Deploy to Vercel

The site is its own Vercel project, next to the web app's.

1. In Vercel, **Add New → Project** and import the repository.
2. **Root Directory**: `apps/site`. Leave "Include files outside the root directory" **on**: the
   build reads `docs/screenshots/`, `docs/social-preview.png` and the web app's touch icon.
3. Framework preset: Astro (auto-detected). Keep the default build command and output directory.
4. No environment variables. Deploy.
5. Pick the address under **Settings → Domains** (a free `your-project.vercel.app` name or a
   custom domain).

The page never names its own address in the code. Canonical and social-card URLs come from
`VERCEL_PROJECT_PRODUCTION_URL`, which Vercel sets on every build, so preview deployments also
point their cards at the production site. Locally they fall back to `http://localhost:4321`.

### When it rebuilds

In a monorepo, Vercel can skip a project when a commit leaves its root directory and workspace
dependencies untouched (check **Settings → Build and Deployment → Root Directory**). That check
does not see the screenshots in `docs/screenshots/`: after regenerating them, redeploy the site
from the Vercel dashboard, or let the next commit under `apps/site` pick them up.

## 3. Security headers

`apps/site/vercel.json` sets the headers. The Content-Security-Policy comes in two parts that the
browser enforces together:

- Astro writes a `<meta>` policy listing a SHA-256 hash for every inline script and style it
  emits (`security.csp` in `astro.config.mjs`). This is what keeps scripts strict.
- The header adds what a `<meta>` tag cannot carry (`frame-ancestors`) and limits images, fonts
  and connections to the site itself. Its `'unsafe-inline'` only defers to the hashed `<meta>`
  policy; with both enforced, an inline script runs only if its hash is listed.

Avoid `style="…"` attributes in the markup: the hashed policy blocks them. Use a class.

## 4. Editing the content

| What | Where |
|---|---|
| Section text | `apps/site/src/components/*.astro`, one file per section |
| Links to the repository and its docs | `apps/site/src/lib/site.ts` |
| Colours, type, spacing | `apps/site/src/styles/global.css` (tokens follow `apps/web/src/app/globals.css`) |
| Title, description, social card | `apps/site/src/layouts/Base.astro` and `SITE` in `site.ts` |
| Screenshots | `docs/screenshots/`, regenerated by `npm run demo:shots -w music-vault-web` and `npm run android:demo-shots` |

The version in the footer is read from the root `package.json`, so a release bump updates it.
Keep every claim on the page in step with the README: the page links to the README's own guides
and should never promise more than they do.
